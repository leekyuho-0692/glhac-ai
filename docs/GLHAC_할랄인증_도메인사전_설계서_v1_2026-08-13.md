# GL-HAC AI 인도네시아 할랄 인증 도메인 사전 설계서 v1

작성일 2026-08-13 · 대상 시스템 glhac-ai-v3

---

## 0. 왜 만드는가

지금까지는 화면 문구 번역만 있으면 됐다. 그런데 인도네시아 원본 서류가 들어오기 시작하면서
같은 개념이 문서·화면·판정·보고서에서 제각각 다뤄지는 문제가 드러났다.

번역기로 끝내면 안 되는 이유는 하나다. **시스템이 문서를 읽고 HPAS 작성 → 원재료 분석 →
Mock Audit → On-site Audit → Audit Report → Fatwa까지 같은 의미 체계로 이해해야 하기
때문이다.** `penyelia halal`을 "할랄 감독자"로 옮기는 것만으로는 그 역할이 **전자서명
대상**이라는 사실이 시스템에 전달되지 않는다.

### 실측으로 확인된 근거

| 사실 | 출처 |
|---|---|
| 인니 실무 자료 재료 136종 중 **90%가 온톨로지 미매칭** | CV CITRA 케이터링 SJPH 매뉴얼 발췌 |
| 재료명이 성분명이 아니라 **상품명**(브랜드+용량) | `Minyak Bimoli 5 Liter`, `DAGING POTONG 1 KG BRAVOO` |
| 서류 분류값이 이미 **도메인 축**을 이룸 | `BAHAN BAKU 16 · BAHAN TAMBAHAN 97 · BAHAN PENOLONG 4 · CLEANING AGENT 6 · KEMASAN 13` |
| `SAN`(플라스틱)이 `pisang`(바나나)로 판정 | 짧은 약어의 부분문자열 오탐 |
| `daging`이 `daging babi` 안에만 존재 | 총칭어 미등재 |

## 1. 현재 용어 자산 — 흩어져 있다

| 위치 | 내용 | 규모 | 서버 사용 |
|---|---|---|---|
| `static/index.html` `EN_STRINGS` | 화면 문구 KO→EN | 2,451 | **불가** |
| `static/index.html` `UI_STRINGS` | 화면 문구 KO→ID | 3,051 | **불가** |
| `intake.py` `DOC_KO/EN/ID` | 서류 종류명 | 33 | 가능 |
| `main.py` `_PRE_RPT_L10N` | 보고서 라벨 | 144 | 가능 |
| `screening.py` | 판정근거 문장·카테고리·유래·증빙·대체재 | 13표 | 가능 |
| `filename_l10n.py` | 파일명 용어·법인격·직책 | 99줄 | 가능 |
| `romanize.py` | 성씨·이름 로마자 | 185 | 가능 |
| DB `ingredient_ontology` | 성분 판정 | 435 | 가능 |

**핵심 문제 두 가지**

1. **가장 큰 두 사전이 프런트엔드 안에만 있다.** 서버가 만드는 보고서·PDF는 이 5,502항목을
   전혀 쓰지 못해 `_PRE_RPT_L10N` 144항목을 따로 만들어야 했다. 같은 말을 두 번 번역한다.
2. **의미가 아니라 문자열만 있다.** `penyelia halal` → "할랄 감독자"는 있어도, 그것이
   *서명 주체*라는 사실은 코드에 흩어져 있다.

## 2. 스키마 — 5계층

```jsonc
{
  "id": "PENYELIA_HALAL",              // ② 표준 키 (시스템 내부 유일값)
  "axis": "ROLE",                       // 도메인 축
  "labels": {                           // ③ 의미 — 언어별 표기
    "id": "Penyelia Halal",
    "ko": "할랄 감독자",
    "en": "Halal Supervisor"
  },
  "surface": {                          // ① 원문·현장 표현 (동의어·약어·표기변형)
    "id": ["penyelia halal", "penyelia", "supervisor halal"],
    "ko": ["할랄감독자", "할랄 감독자", "할랄 책임자"],
    "en": ["halal supervisor"]
  },
  "context": ["HPAS", "AUDIT", "SIGNATURE"],   // ④ 업무 Context
  "actions": {                          // ⑤ 시스템 Action
    "requires_signature": true,
    "role_key": "penyelia_halal",
    "hpas_section": "1.B"
  },
  "authority": "UU 33/2014",            // 법적 근거(있으면)
  "source": ["BPJPH", "field"],         // 법정 표준어 / 현장 표현 출처
  "status": "approved"                  // draft | approved
}
```

### 왜 5계층인가

- **①과 ③을 나누는 이유**: 현장 표기(`bahan utama`, `material utama`)와 표준 의미
  (`Raw Material`)는 다르다. ①은 늘어나고 ③은 고정이다.
- **②가 있어야 하는 이유**: 언어가 늘어도 코드는 `MATERIAL_RAW` 하나만 참조한다.
- **④⑤가 핵심**: 번역기와 도메인 사전을 가르는 지점. `ketidaksesuaian`을 만나면
  "부적합"으로 옮기는 데서 끝나지 않고 **Finding을 생성**해야 한다는 것을 시스템이 안다.

## 3. 도메인 축

| 축 | 무엇 | 표준 키 예 | 시스템 Action 예 |
|---|---|---|---|
| `MATERIAL` | 재료 유형 | `MATERIAL_RAW`, `MATERIAL_ADDITIVE`, `MATERIAL_PROCESSING_AID`, `MATERIAL_CLEANING`, `MATERIAL_LUBRICANT`, `MATERIAL_PACKAGING` | 스크리닝 대상 여부·증빙 요구 |
| `INGREDIENT` | 개별 성분 | 기존 `ing.*` 435항목 | 할랄 판정 |
| `PROCESS` | 공정 | `PPH`, `PROCESS_FLOW`, `SLAUGHTER` | 공정도 요구 |
| `ROLE` | 역할 | `PENYELIA_HALAL`, `AUDITOR_HALAL`, `P3H` | 서명·권한 |
| `ORG` | 기관 | `BPJPH`, `LPH`, `MUI` | 인증번호 발급기관 판별 |
| `AUDIT` | 심사 | `ONSITE_AUDIT`, `NON_CONFORMITY`, `EVIDENCE` | Finding·증빙 생성 |
| `HPAS` | SJPH 문서 | `SJPH`, `HALAL_POLICY`, `INTERNAL_AUDIT`, `MANAGEMENT_REVIEW` | 매뉴얼 섹션 매핑 |
| `FATWA` | 파트와 | `SIDANG_FATWA`, `KEPUTUSAN_FATWA` | 심의·결정문 |
| `DOC` | 서류 종류 | 기존 `DOC_*` 11종 | 체크리스트 |
| `UNIT` | 단위·수량 | `UNIT_PIECE`, `UNIT_KG` | **오역 차단** |

### MATERIAL 축이 즉시 필요한 이유

받은 자료의 `Jenis Bahan` 값이 그대로 이 축이다. 지금은 온톨로지 성분 판정만 있고
**"이 재료가 어떤 성격인지"** 축이 없어서, 세척제·포장재를 성분 사전에 억지로 넣었다.

```
BAHAN BAKU      → MATERIAL_RAW            스크리닝 대상
BAHAN TAMBAHAN  → MATERIAL_ADDITIVE       스크리닝 대상
BAHAN PENOLONG  → MATERIAL_PROCESSING_AID 스크리닝 대상(잔류 확인)
CLEANING AGENT  → MATERIAL_CLEANING       성분 판정 아님 · 설비 세척 절차 검토
KEMASAN         → MATERIAL_PACKAGING      접촉 재질 검토
```

## 4. 단위·수량 사전 — 오역 차단

`3개 → 3 anjing`(개=犬) 같은 사고는 LLM 번역에 맡기는 한 반복된다. 단위는 **결정적 표로
고정하고 LLM 경로에서 제외**한다.

```jsonc
{ "id": "UNIT_PIECE", "axis": "UNIT",
  "labels": { "ko": "개", "id": "buah", "en": "piece" },
  "surface": { "ko": ["개", "個"], "id": ["buah", "pcs", "biji"] },
  "actions": { "translate_by": "table_only",
               "forbid": { "id": ["anjing", "ekor"] } } }
```

- `translate_by: table_only` — 이 항목은 LLM에 넘기지 않는다
- `forbid` — 금지 대역. 번역 결과에 이 말이 나오면 실패로 처리하고 재시도

적용 대상: 개·병·박스·봉지·통·마리(→`ekor`, 동물에만) 등. 실측 자료의
`kg·liter·pcs·galon·sachet·renceng·bungkus·kaleng`은 이미 매칭 정규화에 넣었고,
사전으로 옮기면 번역과 매칭이 같은 표를 쓴다.

## 5. 저장 위치와 소비처

```
app/domain_dict.json      ← 정본 (ontology_data.json과 같은 방식)
app/domain_dict.py        ← 로더·조회 API
   lookup(surface, lang)  → 표준 키
   label(key, lang)       → 표기
   actions(key)           → 시스템 Action
   axis(key)              → 축
```

| 소비처 | 무엇을 얻나 |
|---|---|
| 문서 OCR·파싱 | 원문 용어 → 표준 키 (`Jenis Bahan` 값 정규화) |
| 원재료 매칭 | 인니어 표기 흡수, 단위 제거 |
| HPAS 자동작성 | 섹션 키 매핑 (`hpas_section`) |
| Audit / Mock Audit | `NON_CONFORMITY` → Finding 생성 |
| Fatwa | 결정문 용어 |
| 보고서 3개 언어 | `_PRE_RPT_L10N` 대체 |
| RAG 검색 | 동의어 확장 |
| 번역 | 금지 대역·단위 고정 |

| 단계 | 내용 | 위험 |

| **1** | 스키마 확정 + 로더 구현 + **축 6개 골격 용어 60~80개** 등재 (지금 받은 서류에서 실제로 쓰인 것만) | 없음(추가만) |

| **3** | `_PRE_RPT_L10N` 144항목 이관 → 보고서가 사전을 참조 | 중간(보고서 회귀) |
| **4** | `UI_STRINGS`(ID) 3,051 · `EN_STRINGS` 2,451을 **서버로 이관** → 프런트가 API로 받아감 | **높음** — 화면 전체 영향 |

다만 화면 전체가 걸리므로 시연 이후에 하는 것이 맞다.

## 8. 하지 않을 것

- **총칭어를 억지로 매핑하지 않는다.** `minyak`(기름)·`saus`(소스)는 이름만으로 유래를
  알 수 없다. 할랄로 두면 동물성이 통과하고, 의심으로 두면 식용유까지 전부 의심이 된다.
  **모르면 미판정이 정직한 답이다.**
- **LLM으로 사전을 채우지 않는다.** 실측에서 qwen2.5가 `타우린 → Tauryin`,
  `대상(제조사) → Target`, `바이오로제트 → Baiorojeteu`(실제 상호 BIOROSETTE)로 틀렸다.
  사전은 사람이 확정하고, LLM은 후보 제시까지만.
- **고유명사를 코드에 박지 않는다.** 회사·사람 이름은 데이터(신청서 입력)로 받는다.
  코드에 박으면 그 업체에만 동작한다.
