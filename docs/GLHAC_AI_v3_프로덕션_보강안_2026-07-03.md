# GL-HAC AI v3 프로덕션 보강안

작성일: 2026-07-03  
대상: GL-HAC AI v3  
목적: 현 v3 MVP/설계 산출물을 상용 서비스 수준으로 전환하기 위한 부족분, 누락 기능, 보강 구조, 단계별 구현 기준을 정의한다.

---

## 1. Executive Summary

GL-HAC AI v3는 현재 다음 방향성을 갖는다.

- 할랄 인증 업무의 end-to-end workflow 지원
- Self Declare / Reguler dual pathway 분기
- 신청자, 컨설턴트, 감사원, 샤리아, 운영자, IT 관리자 역할 분리
- 문서/OCR/AI 보조 판단 기반의 인증 업무 자동화
- SIHALAL 및 외부 인증 체계와의 연계 가능성

그러나 현재 구현은 프로덕션 상용 서비스 기준에서 다음 영역이 미흡하다.

1. API 계약서, UI 명세, 테스트, 실제 구현 간 권한/상태/역할 불일치
2. 상태머신은 존재하나 업무 증빙 기반의 전이 조건이 부족
3. 인증서 lifecycle, Fatwa committee, LPH 현장 감사, CAR 시정조치 workflow 미완성
4. AI/OCR 판단의 근거성, 추적성, 검증 체계 부족
5. SQLite 중심 MVP 구조로 데이터 무결성, 테넌트 격리, 감사 추적, 운영 확장성 부족
6. UI는 단일 정적 SPA 성격이 강하며 프로덕션 DataList, i18n, 접근성, 에러 처리 수준 부족
7. 인증/보안/감사/파일 보관/알림/모니터링 등 상용 운영 요건 미충족

본 보강안의 목표는 단순 기능 추가가 아니라, 인증 업무 시스템으로서의 책임 경계와 증빙력을 강화하는 것이다.

## 2. 목표 아키텍처 원칙

### 2.1 Source of Truth 분리

프로덕션에서는 다음 네 가지 정의가 반드시 하나의 기준에서 파생되어야 한다.

- RBAC/ABAC 권한 매트릭스
- 상태머신 전이표
- API 계약서
- 화면 노출/버튼 활성화 정책

현재처럼 문서, 테스트, 코드, 화면이 개별적으로 권한을 정의하면 인증서 발급, Fatwa 승인, 갱신, unlock 같은 핵심 행위에서 책임 소재가 무너진다.

### 2.2 Evidence-first Workflow

상태 전이는 역할만으로 허용하지 않는다. 다음 증빙 조건을 함께 만족해야 한다.

- 필수 문서 제출 여부
- 문서 검토 승인 여부
- LPH 배정 및 현장 감사 완료 여부
- Audit finding/CAR 종료 여부
- Fatwa 심의 완료 여부
- 결제 완료 여부
- 인증 범위 확정 및 잠금 여부
- 최종 산출물 생성 및 서명 여부

### 2.3 Human-in-the-loop AI

AI/OCR은 자동 판정자가 아니라 인증 실무자의 보조자로 설계한다.

- AI는 추천, 추출, 위험도, 불일치 탐지를 제공한다.
- 최종 판단은 역할 권한을 가진 사용자만 수행한다.
- AI 결과는 원문 근거, 신뢰도, 모델 버전, reviewer override 이력과 함께 저장한다.

### 2.4 Auditability by Default

상용 인증 업무에서 모든 중요 행위는 감사 가능해야 한다.

- 누가
- 언제
- 어떤 권한으로
- 어떤 데이터에 접근했고
- 무엇을 변경했으며
- 변경 전후 값은 무엇이고
- 어떤 근거로 승인/반려했는지

읽기, 다운로드, AI 재분석, 권한 변경까지 감사로그 대상에 포함한다.

## 3. 핵심 Gap 분석

### 3.1 RBAC/ABAC 권한 불일치

현재 확인된 대표 불일치 항목은 다음과 같다.

| 영역 | 문서/명세 기대 | 구현상 위험 | 보강 방향 |
|---|---|---|---|
| 인증서 발급 | Sharia + Operator 또는 명확한 2인 승인 | Operator 단독 발급 가능 구조 | 2단계 승인 또는 Operator 발급 + Sharia 사전 승인 조건 강제 |
| 인증서 unlock | Operator/IT 성격 | Consultant 권한으로 열릴 수 있음 | Operator 승인 + IT override + 사유 필수 |
| 갱신 | 운영/IT 통제 성격 | Applicant/Consultant 흐름과 혼재 | 갱신 신청과 갱신 승인 권한 분리 |
| Fatwa 문서 조회 | Sharia/Operator 제한 필요 | 로그인 사용자 전체 접근 위험 | case ownership + role + document classification 기반 제어 |
| onsite checklist | Auditor/Sharia/Operator 중심 | Consultant 포함 가능 | 작성, 검토, 확정 권한 분리 |
| LPH reference admin | IT/Admin 성격 | Consultant 접근 가능성 | Admin only 또는 Operator managed로 정리 |

보강 원칙:

- 역할 기반 RBAC만으로 부족하다. 케이스 소속, 조직, 배정 여부, 현재 상태, 문서 등급을 포함한 ABAC가 필요하다.
- 모든 endpoint에 `action_id`를 부여하고, `ROLE_ACTION_MATRIX`에서 검증한다.
- UI 버튼 노출은 API 권한을 그대로 조회해서 렌더링한다.

권장 action_id 예시:

```text
case.read
case.create
case.transition
case.assign_consultant
document.upload
document.review
audit.plan
audit.submit_checklist
audit.close_car
fatwa.propose
fatwa.approve_final
certificate.issue
certificate.unlock
certificate.revoke
certificate.renew
admin.user.manage
admin.role.manage
admin.rule.manage
```

## 4. 프로덕션 권한 모델

### 4.1 역할 정의

| Role | 설명 | 주요 책임 |
|---|---|---|
| client | 신청 기업/개인 | 신청, 자료 제출, 보완, 결제, 결과 조회 |
| consultant | 컨설턴트/멘토 | 신청 보조, 문서 검토 지원, 보완 요청 |
| auditor | 감사원/LPH | 현장 감사, finding 작성, CAR 검토 |
| sharia | Fatwa/Sharia 담당 | Fatwa 검토, 할랄 적합성 판단, 최종 의견 |
| operator | 운영자/BPJPH 업무 담당 | 배정, 최종 행정 승인, 인증서 발급 관리 |
| admin | IT/시스템 관리자 | 계정, 권한, 시스템 설정, emergency override |

### 4.2 권한 설계 방식

권한은 다음 네 단계로 판단한다.

1. Authentication: 로그인 및 토큰 유효성
2. Role permission: action_id 수행 가능 역할인지
3. Resource scope: 같은 org, 배정된 case, 담당 LPH, 담당 committee인지
4. State guard: 현재 case 상태에서 수행 가능한 행위인지

예시:

```text
certificate.issue 허용 조건
- role: operator
- case.status: fatwa_final_approved
- certificate.status: draft 또는 pending_issue
- required_documents: all approved
- payment.status: paid
- audit.status: closed
- fatwa.status: final_approved
- scope_locked: true
- sharia_decision_id exists
- operator가 발급 사유 입력
```

### 4.3 2인 승인 정책

다음 행위는 2인 승인 또는 maker-checker 구조를 권장한다.

- Fatwa 최종 승인
- 인증서 발급
- 인증서 unlock
- 인증서 철회
- 인증 범위 변경
- 케이스 강제 전이
- Rule version 변경
- 관리자 권한 부여

## 5. 상태머신 보강안

### 5.1 상태군 재정리

상태는 UI 표시용 상태와 내부 검증 상태를 분리한다.

| 상태군 | 대표 상태 | 목적 |
|---|---|---|
| intake | draft, submitted, intake_review | 접수 및 기본 검토 |
| pathway | pathway_assessment, self_declare, reguler | 경로 판정 |
| document | document_requested, document_review, document_approved | 서류 제출/검토 |
| payment | invoice_issued, payment_pending, payment_paid | 비용 처리 |
| lph | lph_assigned, audit_scheduled, audit_completed | LPH/감사 |
| car | finding_open, car_submitted, car_closed | 부적합 시정 |
| fatwa | fatwa_draft, fatwa_review, fatwa_final_approved | Fatwa 심의 |
| certificate | cert_draft, cert_issued, cert_active, cert_suspended, cert_revoked, cert_expired | 인증서 lifecycle |

### 5.2 필수 Guard

| 전이 | 필수 guard |
|---|---|
| submitted -> intake_review | 신청자 기본정보, 제품정보, 사업자 정보 완비 |
| intake_review -> pathway_assessment | 중복 신청 없음, 최소 문서 세트 있음 |
| pathway_assessment -> self_declare | Self Declare 기준 충족, 위험 성분 없음 |
| pathway_assessment -> reguler | Self Declare 제외 사유 기록 |
| document_review -> document_approved | 모든 필수 문서 승인 또는 면제 사유 |
| lph_assigned -> audit_scheduled | 감사자 배정, 일정, 범위 확정 |
| audit_completed -> finding_open | finding 존재 시 자동 분기 |
| finding_open -> car_closed | 모든 CAR 승인 |
| fatwa_review -> fatwa_final_approved | quorum, 결론, 근거 문서, 반대 의견 기록 |
| fatwa_final_approved -> cert_issued | 결제 완료, 문서 잠금, 인증 범위 잠금, 발급 승인 |
| cert_active -> cert_suspended | 사유, 기간, 통지 기록 |
| cert_suspended -> cert_active | 재심사 또는 보완 승인 |
| cert_active -> cert_revoked | 철회 사유, 승인권자, 통지 기록 |

### 5.3 Raw transition 제한

관리자 raw transition은 프로덕션에서 기본 비활성화한다.

- feature flag 필요
- admin + operator 2인 승인
- 사유 필수
- before/after snapshot 저장
- 전이 후 자동 검증 job 실행

## 7. AI/OCR 프로덕션 보강안

### 7.1 AI 기능 범위

AI는 다음 네 영역으로 제한해 도입한다.

1. 문서 OCR 및 필드 추출
2. 원재료/첨가물/공정 위험 신호 탐지
3. 제출 문서 간 불일치 탐지
4. 보고서 초안 및 보완 요청 문안 생성

AI가 직접 수행하면 안 되는 행위:

- Fatwa 최종 판단
- 인증서 자동 발급
- 신청 반려 확정
- 사람 승인 없는 상태 전이

### 7.2 AI 결과 저장 구조

```text
document_ai_extractions
- id
- document_version_id
- model_provider
- model_name
- model_version
- prompt_version
- extraction_schema_version
- extracted_json
- confidence
- evidence_spans
- page_refs
- bbox_refs
- risk_flags
- reviewer_status
- reviewer_id
- reviewer_note
```

### 7.3 AI 평가 체계

운영 전 최소 평가셋:

- 라벨 문서 OCR 100건
- 성분표 추출 100건
- 사업자/제품 정보 문서 50건
- 할랄/비할랄 위험 성분 케이스 100건
- 문서 불일치 케이스 50건

목표 지표:

| 항목 | 목표 |
|---|---|
| OCR field extraction F1 | 0.90 이상 |
| 고위험 성분 recall | 0.98 이상 |
| 고위험 성분 precision | 0.90 이상 |
| 문서 불일치 탐지 recall | 0.90 이상 |
| hallucination rate | 1% 이하 |
| reviewer override rate | 초기 20% 이하, 안정화 후 10% 이하 |

### 7.4 AI 안전장치

- AI 응답 JSON schema validation
- 원문 근거 없는 판단 금지
- confidence 낮으면 자동 `needs_human_review`
- 모델/프롬프트 버전 고정
- 재분석 시 이전 결과 보존
- AI 결과 사용 화면에 근거와 불확실성 표시

## 9. 보안 보강안

### 9.1 인증

현재 커스텀 HMAC JWT는 MVP에는 가능하나 프로덕션에는 다음 보강이 필요하다.

- Access token + refresh token
- token rotation
- session revocation
- logout all devices
- asymmetric signing 또는 KMS-backed signing
- key rotation
- password policy
- MFA optional, admin MFA required

### 9.2 인가

- endpoint별 action_id mandatory
- resource ownership check mandatory
- admin override도 audit reason 필수
- role 변경은 maker-checker 적용

### 9.3 파일 보안

- MIME sniffing
- 파일 크기 제한
- 확장자 allowlist
- 바이러스/멀웨어 스캔
- object storage private bucket
- signed URL short TTL
- hash 기반 무결성 확인
- 다운로드 audit log

### 9.4 감사로그

감사로그 대상:

- 로그인 성공/실패
- 권한 변경
- case 조회
- 문서 조회/다운로드
- 문서 업로드/삭제
- 상태 전이
- AI 분석 실행
- AI 결과 override
- Fatwa 승인
- 인증서 발급/정지/철회
- 외부 연동 송수신

## 15. 수용 기준

프로덕션 전환 완료 판단 기준은 다음과 같다.

1. API 계약서와 구현 권한이 100% 일치한다.
2. UI 버튼 권한과 API 권한이 동일한 action_id를 사용한다.
3. 인증서 발급은 필수 증빙과 승인 없이 불가능하다.
4. 모든 protected transition은 감사로그와 before/after snapshot을 남긴다.
5. 모든 문서는 버전, 해시, 검토 상태, 다운로드 로그를 가진다.
6. AI 결과는 원문 근거, confidence, 모델 버전, reviewer 이력을 가진다.
7. PostgreSQL 기반 migration이 dev/staging/prod에서 동일하게 동작한다.
8. role별 e2e 테스트가 통과한다.
9. 인증서 QR 검증, 정지, 철회, 갱신 lifecycle이 동작한다.
10. 장애, 백업, 복구, 모니터링, 알림 운영 절차가 문서화되어 있다.

## 16. 결론

GL-HAC AI v3의 방향성은 상용 할랄 인증 업무 플랫폼으로 확장 가능하다. 다만 현재 상태는 기능 데모와 프로덕션 설계 사이에 간극이 있다. 특히 인증서 발급, Fatwa, LPH 감사, 문서 증빙, AI 판단, 권한 제어는 규제/인증 업무에서 책임이 큰 영역이므로 우선적으로 보강해야 한다.

가장 먼저 해야 할 일은 기능 추가가 아니라 정합성 잠금이다.

1. 권한 매트릭스 단일화
2. 상태머신 단일화
3. API/UI/테스트 자동 검증
4. 증빙 기반 guard 적용
5. 감사 가능한 인증서 lifecycle 구축

이 순서로 보강하면 MVP를 무리하게 확장하는 방식이 아니라, 상용 인증 업무 시스템으로 안정적으로 전환할 수 있다.
