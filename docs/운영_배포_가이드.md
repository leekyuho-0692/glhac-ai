가비아 서버에서 GL-HAC 을 운영하는 사람을 위한 문서입니다.
**무엇을 어떻게 하는지**와 **잘못됐을 때 어떻게 되돌리는지**를 담았습니다.

마지막 확인 2026-10-13.

## 1. 지금 무엇이 어디서 도는가


## 3. 배포하는 법

### 방법 A — GitHub 에서 (권장)

저장소 → **Actions** → **Deploy (가비아)** → **Run workflow**
→ 입력칸에 `deploy` 를 적고 실행.

`deploy` 를 적어야만 도는 이유는, 실수로 눌러 배포되는 일을 막기 위해서입니다.
백엔드는 **테스트가 통과해야 배포**합니다 — 깨진 코드는 서버에 올라가지 않습니다.

### 방법 B — 내 컴퓨터에서

```bash
git clone https://github.com/leekyuho-0692/glhac-ai.git
cd glhac-ai
bash scripts/deploy.sh                # 배포
bash scripts/deploy.sh --dry-run      # 무엇이 바뀌는지만 보기
bash scripts/deploy.sh --rollback     # 직전 백업으로 되돌리기
```

홈페이지(`glhac-web`)도 같은 방식입니다.

SSH 키가 기본 위치(`~/Downloads/SSH_KeyPair-260908134815.pem`)에 없으면
`GLHAC_SSH_KEY=/경로/키.pem` 으로 알려 주세요.

### 배포가 실제로 하는 일

```
백업 → 전송 → 소유권·SELinux 라벨 → 서비스 재기동 → 헬스체크 → 공개 URL 확인
                                                      ↓ 실패하면
                                              직전 백업으로 자동 복구
```

**헬스체크가 통과해야 끝난 것으로 봅니다.** 실패하면 그 자리에서 되돌리고
서버 로그 마지막 줄을 보여 줍니다.

```bash
  -H 'Content-Type: application/json' \
```

하면 되는지** 적혀 있습니다. 시스템은 멈추지 않고 수기 모드로 계속 돕니다.

## 6. 데이터 백업과 복구

### 자동 백업

**매일 새벽 3시(KST)** 에 돕니다. 85MB → 53MB 로 압축되고 4초쯤 걸립니다.
14일치를 보관합니다.

```bash
sudo systemctl list-timers glhac-backup.timer   # 다음 실행 시각
sudo tail -20 /var/log/glhac-backup.log         # 최근 기록
sudo ls -lh /var/backups/glhac/                 # 보관 중인 백업
```

그냥 복사하지 않고 `sqlite3 .backup` 을 씁니다 — **DB 가 WAL 모드**라 앱이 쓰는 중에
파일만 복사하면 앱이 기록한 최근 변경분(WAL-wal 파일에 있음)이 백업에서 빠져
복구할 때 데이터 손실이 생깁니다. `.backup()` 을 쓰면 이를 방지합니다.
뜬 뒤에는 무결성 검사와 내용 확인(케이스가 0건이면 실패 처리)까지 합니다.

### 지금 당장 한 번 더 뜨기

```bash
sudo /usr/local/bin/glhac-backup.sh
```

### 복구

```bash
# 1) 풀고 확인 — 'ok' 가 나와야 한다
gunzip -c /var/backups/glhac/glhac_v3-YYYYMMDD-HHMMSS.db.gz > /tmp/r.db
sqlite3 /tmp/r.db "PRAGMA integrity_check"
sqlite3 /tmp/r.db "SELECT COUNT(*) FROM case_application"

# 2) 바꿔치기
sudo systemctl stop glhac-app

# 현재 DB 를 보존(before-restore-YYYYMMDD.db 형식)
NOW=$(date +%Y%m%d%H%M%S)
sudo /opt/glhac/.venv/bin/python << PYEOF
import sqlite3
conn = sqlite3.connect("/var/lib/glhac/glhac_v3.db")
backup_conn = sqlite3.connect(f"/var/lib/glhac/glhac_v3.db.before-restore-{$NOW}")
conn.backup(backup_conn)
backup_conn.close()
conn.close()
print(f"현재 DB 보존: /var/lib/glhac/glhac_v3.db.before-restore-{$NOW}")
PYEOF

# WAL 파일 정리 — 복원한 파일과 충돌 방지
sudo rm -f /var/lib/glhac/glhac_v3.db-wal /var/lib/glhac/glhac_v3.db-shm

# 복구본 적용
sudo cp /tmp/r.db /var/lib/glhac/glhac_v3.db
sudo chown rocky:rocky /var/lib/glhac/glhac_v3.db

sudo systemctl start glhac-app

# 3) 확인
curl -s -o /dev/null -w '%{http_code}\n' https://glhac.co.kr/ui/
```

**바꿔치기 전에 현재 DB 를 보존합니다(before-restore-* 파일로).** 복구본이 예상과 다를 수 있기 때문입니다.
**WAL 파일 정리가 필수입니다** — 남은 WAL 파일이 복구본에 재적용되면 DB 가 섞입니다.

```bash
sudo nginx -t && sudo systemctl reload nginx
```

### 접근 로그 중복 문제

uvicorn 의 기본 접근 로그와 앱의 JSON 접근 로그가 함께 journald 로 기록되어 같은 요청이 두 번 기록됩니다(저장 용량 중복). 실제 중복 여부는 `journalctl -u glhac-app -n 20` 으로 먼저 확인하세요.
systemd 유닛 파일에서 ExecStart 에 `--no-access-log` 를 추가하면 uvicorn 기본 로그를 비활성화할 수 있습니다:

```bash
# /etc/systemd/system/glhac-app.service 확인
grep ExecStart /etc/systemd/system/glhac-app.service

# --no-access-log 추가 (예시)
ExecStart=/opt/glhac/.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8800 --no-access-log

# 유닛 파일을 고친 뒤에는 반드시
sudo systemctl daemon-reload && sudo systemctl restart glhac-app
```

### 로그 저장 기간 관리

journald 로그가 무한정 쌓이지 않게 보존 기간을 설정합니다:

```bash
# /etc/systemd/journald.conf 수정
sudo sed -i 's/^#SystemMaxUse=/SystemMaxUse=/' /etc/systemd/journald.conf
sudo sed -i 's/SystemMaxUse=.*/SystemMaxUse=5G/' /etc/systemd/journald.conf
sudo sed -i 's/^#MaxRetentionSec=/MaxRetentionSec=/' /etc/systemd/journald.conf
sudo sed -i 's/MaxRetentionSec=.*/MaxRetentionSec=30day/' /etc/systemd/journald.conf
sudo systemctl restart systemd-journald
```

### 컨테이너 운영 (미지원)

Dockerfile 과 docker-compose.yml 은 로컬 개발용입니다. **운영 방식(systemd + venv:8800)과 다르며 검증되지 않았습니다.**
배포는 `bash scripts/deploy.sh` 를 사용하세요.

### 배포된 빌드 확인

`deploy.sh` 는 배포 때마다 `app/VERSION`(커밋 해시·시각)을 만들어 올리고, 끝에서 `/health` 의 `build` 값과 비교해 다르면 경고합니다.
수동으로 볼 때는 `curl -s http://127.0.0.1:8800/health` 의 `build` 를 확인하세요(`unknown` 이면 VERSION 없이 배포된 것).

## 8. 겪었던 문제들

실제로 한 번씩 겪은 것들입니다. 같은 증상이 보이면 여기부터 보세요.

### 화면을 고쳤는데 그대로다

`/assets/` 는 **1년 immutable 캐시**입니다. 번들 내용만 바꾸고 파일명을 그대로
두면 이미 방문한 브라우저가 옛 파일을 계속 씁니다.

→ 파일명을 바꾸고 `index.html` 의 참조도 함께 고치세요.
배포 스크립트가 이 경우를 **배포 전에 막습니다.**

HTML 자체는 `no-cache` 라 바로 반영됩니다(`/` 와 `/board/` 둘 다).

### 배포 후 서비스가 안 뜬다

소유권을 `root` 로 바꾸면 앱이 파일을 못 읽습니다. 서비스는 `rocky` 로 돕니다.

```bash
sudo chown -R rocky:rocky /opt/glhac/app
sudo systemctl restart glhac-app
```

### 홈페이지가 403 이다

SELinux 라벨이 빠진 것입니다.

```bash
sudo restorecon -R /var/www/glhac-home
```

### OCR 이 안 된다

서버 CPU 빌드에서 oneDNN 가속 경로가 터집니다. 꺼 두었습니다(기본값).
혹시 `GLHAC_OCR_MKLDNN=1` 이 들어가 있다면 빼세요.

`"ocr": {"installed": false}` 로 나오면 패키지가 빠진 것입니다.

```bash
sudo -u rocky /opt/glhac/.venv/bin/pip install 'paddlepaddle==3.3.1' 'paddleocr==3.7.0'
sudo dnf install -y mesa-libGL glib2      # libGL 없으면 임포트부터 실패한다
sudo systemctl restart glhac-app
```

### 게시판에 글이 안 써진다

도배 차단이 같은 IP 에서 **시간당 3건**으로 잡혀 있습니다.
행사처럼 한 회선에서 여럿이 쓰는 자리면 잠시 올리세요.

```bash
sudo sed -i 's/^GLHAC_BOARD_RATE_MAX=.*/GLHAC_BOARD_RATE_MAX=50/' /opt/glhac/.env
sudo systemctl restart glhac-app
# 끝나면 3 으로 되돌릴 것
```

## 9. 챙겨야 할 일

| 언제 | 무엇 |

| 배포할 때마다 | 공개 URL 3곳이 200 인지 |

| 수시 | 디스크 여유(현재 490GB 남음) |

```bash
# 인증서 확인
sudo certbot certificates | grep -E "Certificate Name|Expiry"

# 자동 갱신 상태 확인 (다음 갱신 예정일이 '몇 시간/일 남음' 이어야 함)

# 만약 NEXT 가 'n/a' 면 갱신 타이머가 비활성화된 것 — 재시작
```

`/tmp` 에 풀어 건수만 세어 봐도 충분합니다.

## 10. 개인정보 암호화

CaseApplication, ExternalIdentity, Org, ConsultantProfile 의 민감 컬럼(이름, 이메일, 전화, 주소, 사업자등록번호 등)을 AES-256-GCM 으로 암호화할 수 있습니다.

### 켜는 법

로컬 컴퓨터에서 한 줄입니다. SSH 키와 접근 권한이 필요합니다.

```bash
bash scripts/encryption_on.sh
```

스크립트가 다음을 자동으로 합니다.
  1. DB 백업 (`/var/lib/glhac/glhac_v3.db.bak-encryption-<타임스탬프>`)
  2. 암호화 키 확인 (없으면 중단 — 아래 참조)
  3. `.env` 에 `GLHAC_ENCRYPTION=1` 추가
  4. 앱 서비스 재기동
  5. 기존 평문 데이터를 암호화로 변환 (`encrypt_backfill.py`)
  6. 모든 데이터가 암호화됐는지 검증

### 암호화 키 생성 및 보관

스크립트가 `GLHAC_ENC_KEY` 를 요구합니다. 미설정이면 중단됩니다.

키는 32바이트 난수(base64 44자 또는 hex 64자)입니다. 생성하는 법:

```bash
python3 -c "import secrets,base64;print(base64.b64encode(secrets.token_bytes(32)).decode())"
```

출력 예: `AAAA...aaa=` (44자)

이 키를 **두 곳**에 보관하세요.
1. `/opt/glhac/.env` 에 `GLHAC_ENC_KEY=<그 값>` (scaler가 제공)
2. **NAS 등 오프사이트** — 서버 디스크가 사라져도 잃지 않도록

**이 키를 잃으면 암호화된 서류와 개인정보는 영구히 복구 불가능합니다.**

### 기존 백업 파일의 평문 데이터

`/var/backups/glhac/` 의 자동 백업(14일 순환)은 여전히 평문으로 남습니다.
정기적으로 정리하거나 별도 보안 저장소로 이전하세요.
수동 백업(`bak-*` 파일)도 마찬가지입니다.

### 끄는 법

혹시 문제가 생기면 한 줄입니다.

```bash
sed -i '/^GLHAC_ENCRYPTION=/d' /opt/glhac/.env
sudo systemctl restart glhac-app
```

데이터는 손상되지 않습니다. `dec()` 함수가 평문과 암호문 모두 처리하므로 계속 읽힙니다.
단, 암호화 키(`GLHAC_ENC_KEY`)는 계속 필요합니다 — 없으면 암호화된 행은 읽을 수 없습니다.

### 키 회전

현재 지원하지 않습니다. `crypto.py` 의 `ACTIVE_VER = "v1"` 은 신규 암호화가 붙이는
버전이고, `v2`/`v3` 환경변수(`GLHAC_ENC_KEY_V2`, `GLHAC_ENC_KEY_V3`)는 **읽기**만
지원합니다(기존 데이터 호환 목적).

### 키 역할 분리 (감사 키 · 인증서 서명 키)

기본값에서는 `GLHAC_SECRET` 하나가 로그인 토큰, 감사 해시체인(WorkflowEvent·AuditLog), 인증서 서명을 모두 맡습니다.
그래서 로그인 키를 회전하면 감사체인·인증서 검증이 깨집니다. 아래 두 키를 따로 두면 분리됩니다(둘 다 선택).

| 환경변수 | 맡는 일 | 미설정 시 |
|---|---|---|
| `GLHAC_SECRET` | 로그인 토큰 서명(그 외 기존 기록의 검증) | (필수) |
| `GLHAC_AUDIT_KEY` | **새로 기록되는** 감사체인 행의 HMAC | 기존처럼 `GLHAC_SECRET` |
| `GLHAC_CERT_SIGN_KEY` | **새로 서명하는** 인증서 전자서명 | 기존처럼 `GLHAC_SECRET` |

도입 절차:

1. 키 생성: `python3 -c "import secrets; print(secrets.token_urlsafe(48))"` (두 키 각각)
2. `/opt/glhac/.env` 에 `GLHAC_AUDIT_KEY=...`, `GLHAC_CERT_SIGN_KEY=...` 추가 후 서비스 재기동.
3. **키는 서버 밖(오프사이트·비밀번호 관리자)에도 따로 보관**합니다. `.env` 백업과 같은 곳에만 두지 마세요.
4. 도입 후 새 기록은 서명값 앞에 `k2:` 구분자가 붙습니다. 구분자가 없는 이전 기록은 계속 `GLHAC_SECRET` 으로 검증합니다
   (키를 섞어 쓰는 체인도 무결로 검증됨).
5. 도입 **후에는** `GLHAC_SECRET` 을 회전해도 `k2:` 기록의 감사체인·인증서 검증은 유지됩니다.
   다만 구분자 없는 이전 기록은 옛 `GLHAC_SECRET` 이 필요하므로, 회전 전에 이전 기록 구간은 별도 보관(옛 키 보관)하세요.

주의: **감사 키·인증서 서명 키를 잃으면 그 이후(`k2:`) 기록은 검증할 수 없습니다.** 키를 바꾸는(회전) 기능은 없습니다.
키를 지우거나 바꾸면 `k2:` 행은 위조로 판정됩니다. 기존 `GLHAC_AUDIT_CHAIN_EPOCH` 경계 판정은 그대로입니다.

## 11. 지금 알려진 약점

정리해 두는 편이 안전한 것들입니다.

- **데모 계정이 열려 있습니다.** `admin/admin`, `consultant1/pw` 등이
  인터넷에서 그대로 들어갑니다. 실제 업체 서류가 들어 있으므로
  비밀번호를 바꾸거나 접속 IP 를 제한하세요.
- **백업이 같은 서버에만 있습니다.** 서버 자체가 사라지면 백업도 함께 사라집니다.
  중요해지면 외부(NAS·클라우드)로 한 벌 더 빼야 합니다.
- **맥에 옛 시스템이 아직 돕니다.** 별도 DB 를 쓰므로, 어느 쪽이 정본인지
  헷갈릴 수 있습니다.
- **암호화 키를 잃으면 복구 불가능합니다.** 키 회전이 없으므로, 키 관리가 중요합니다.
